## 零、先定边界：系统端只干三件事

**看谁需要人 → 把人派给谁 → 记下结果。**

| # | 职责 | 对应层 | 落成的界面 |
|---|---|---|---|
| 1 | **看谁需要人** | L1 证据 → L2 基线 → L3 分层 | 预警列表 + 每条预警的"为什么" |
| 2 | **把人派给谁** | L4 关系连续谱路由 | 通知记录 + 超时升级 + 待接池 |
| 3 | **记下结果** | 处置结论 → 台账 → 指标 | 处置表单 + 导出 + 看板 |

**任何不服务这三件事的功能，都可以不做。** 这是本文件后面「功能范围」清单的唯一判据。

同时系统端要同时满足三个用途，优先级从高到低：

| 优先级 | 用途 | 含义 |
|---|---|---|
| P0 | **业务能跑** | 承办人真的愿意点，8 周不断线 |
| P1 | **机制可证伪** | 指标能从系统里自然长出来，不用二次统计 |
| P2 | **端到端可跑通** | L1→L4 全链路能跑起来，不是静态界面 |

> P2 只影响"哪三屏先做对"，不该让任何功能为了好看而存在。

### 0.1 功能范围与推进节奏

当前目标只有一个：**把系统搭出来，跑通主链路。** 所有面向「社区实际运营」和「商业化」的能力，设计保留、开发后置。

| 状态 | 含义 | 处理方式 |
|---|---|---|
| **本期** | 现在就做 | 正常开发 |
| **暂缓** | 设计已定，开发后置 | 规格写全、表和接口预留，页面不排期 |
| **不做** | 明确不做 | 写明原因，避免误加 |

**暂缓清单**（都是社区真跑起来才会用到的）：

| 项 | 为什么暂缓 |
|---|---|
| 批量 Excel 导入 | 本期手工建 10–20 个账号够用 |
| 人员管理（账号 CRUD） | 固定演示账号，不做增删改 |
| 工单补录 | 线下处理的单事后补登，暂不需要 |
| 老人退出 / 身故流程 | 真实运营才会遇到 |
| 夜间 / 节假日值班 | 凌晨触发的承接人安排，暂缓 |
| 距离派单扩圈（3→5→10km） | 没有真实坐标转不动，先按片区 |
| 服务单未出发自动释放 | 先用手动退回 |
| 真实支付通道 | 需商户号与企业主体，只做记账 |
| 大屏可视化 | 后置 |
| 监测等级 A/B/C/D 四档 | 先两档：参与监测 / 仅建档 |

**保留项**（容易被误当成「运营功能」，实际是研究/合规需要）：台账 CSV 导出、审计日志。这两个不算运营负担，不要划进暂缓。

> **原则：规格不删，只标状态。** 将来要落地时按这份清单逐项补齐即可，不用重写设计。

## 一、角色与人员配置（v0.3）

### 1.0 先统一四个称呼

这几个词一混，后面全乱。

| 称呼 | 在哪一侧 | 具体指 | 谁能当 |
|---|---|---|---|
| **主责人** | 关系侧 | 某一层里**必须回执**的那个人 | **通常是家人**；无家人时才是志愿者 |
| **知会** | 关系侧 | 同层里只需知情、可静默的人 | 家人、志愿者、邻居 |
| **承办人** | 社区侧 | 接核验单、填处置结论的社区工作人员 | 社区工作者 |
| **管理员** | 社区侧 | 建档、配关系链、配参数、导数据 | 社区指定 1–2 人 |

> **主责人不是承办人。** 主责人在老人亲属里，负责"先去看一眼"；承办人在社区，负责"确认这件事了结"。v0.2 把社区侧那个人叫"处置人"，和"主责人"读起来像同一类角色，容易混——v0.3 统一改叫**承办人**。

**关于网格员：** 网格员已并入社区工作者队伍统一管理，系统里**不再单列"网格员"这个角色**。但各地称呼不同（楼栋长、包片干部、村干部、专职网格员），所以**角色显示名可配**，底层只有一个"承办人"身份。

### 1.1 人不是角色，人有两层身份

v0.1 把"家属 + 结对志愿者"合成一个"关系人"角色，留下一个硬伤：**老人端四键产生的四类服务单，系统里没有人能接**——志愿者被锁在"关系人"里只能回执，社区工作者又不可能跑去帮人买米。

改成两层：

| 层 | 回答什么 | 取值 |
|---|---|---|
| **关系身份** | 这个人跟**这位老人**是什么关系 | 家属 / 结对志愿者 / 邻居·楼栋长 |
| **职能身份** | 这个人在系统里**能操作什么** | 居民 / 关系人 / 服务承接人 / 承办人 / 管理员 |

一个账号可同时持多个职能身份；关系身份按"老人"逐条登记，不是全局属性。

| 人 | 关系身份 | 职能身份 |
|---|---|---|
| 女儿 李敏 | 家属（责任组主责） | 关系人 + 服务承接人（能代购、能陪诊） |
| 儿子 李强 | 家属（责任组成员·知会） | 关系人 + 服务承接人 |
| 王姨 | 结对志愿者 | 关系人 + 服务承接人 |
| 陈师傅 | 可能是某位老人的邻居 | 承办人（社区工作者） |
| 社区 小张 | — | 管理员 |

### 1.2 责任组：兄弟姐妹可以组队

**固定结对不是必选项，是选项。** 但**鼓励**——不结对就只能靠公共池，响应必然慢。

第 1 层支持三种形态，管理员按社区实际选：

| 形态 | 结构 | 适用 |
|---|---|---|
| **责任组**（推荐） | 多个家属（常见是兄弟姐妹）组成一个组，组内指定 1 个主责 | 有多个子女、子女异地 |
| **单点** | 一个人 | 只有一个可靠联系人 |
| **结对志愿者** | 志愿者个人或小组 | 无家属 / 家属长期失联 |

责任组规则：

- 组内**自定 1 个主责**，社区只登记、不指定——家里谁说话算数，社区判断不了
- 主责可在组内随时移交，移交留痕（这是"结对岗位接续率"的数据源）
- 组内其他人都是知会，**知会点回执同样有效**，但只有主责能停计时
- 组可随时增减人，不需要重建关系链

> 这条直接回应报告四（四）：固定结对仅 5.3%。**不要求每个老人都结成对，但要求"有组可找"**——组比个人稳，一个人退出了组还在。

### 1.3 主责人：默认取谁

老人端 6.2 写紧急单"立即通知全部关系人"。但全部通知 = 责任分散，谁都以为别人去了。所以每层要有一个**必须回执**的人。

**基本规则：**

- 每层 **1 个主责 + N 个知会**
- 主责**必须回执**；知会可静默
- 主责无响应 → 计入"家属确认率"的未响应，并触发升级

**五种候选规则，优缺点如下：**

| 方案 | 规则 | 优点 | 缺点 |
|---|---|---|---|
| **A 同住家属** | 与老人同住者优先 | 到场最快，几分钟就能到门口；老人最认 | 同住者可能白天上班（报告已说"同住≠有即时感知者"）；只有 50% 的老人有同住家属 |
| **B 第一顺位** | 建档时管理员排的第一个 | 简单、稳定、可解释 | 通常按长幼排，跟"谁真管事"无关；容易挂名 |
| **C 组内自定** | 责任组自己选一个 | 最贴家庭实际；责任认同最强 | 需要家属配合点一下；没人愿意选时卡住 |
| **D 最近回执者** | 近 30 天回执最快的人 | 用行为选人，比关系名义准 | 冷启动没数据；会漂移，老人要重新适应 |
| **E 距离最近** | 按登记住址算 | 到场快 | 距离 ≠ 关系；还要采集住址，增加建档负担 |

**建议：不做单选，做一条取值链。**

```
① 有责任组 → 组内自定（C）
② 无组，有同住家属 → 同住者（A）
③ 无同住 → 第一顺位（B）
④ 都没有 → 结对志愿者
⑤ 再没有 → 跳过该层，直接到承办人
```

理由：C 最贴实际但依赖家属配合，A 最快但只覆盖一半，B 最稳但容易挂名。**单用任何一个都会在某类家庭上失效**，串起来才兜得住。

**再加一条动态校准（这条比默认值重要）：**

连续 3 次触发、主责都没回执 → 系统给管理员推一条"建议调整主责"，由管理员和家属沟通后改。
没有这条，挂名主责会永久占位，机制看起来在跑、实际全靠升级兜底。

> 同步通知是并发触达，主责是责任归属，两者不冲突。

### 1.4 权限矩阵（按职能身份）

| 能力 | 居民 | 关系人 | 服务承接人 | 承办人 | 管理员 |
|---|---|---|---|---|---|
| 查看老人档案 | 自己 | 关联范围内（不含完整病史） | 接单后可见 | 负责范围内 | 全部 |
| 播放原始录音 | 自己发的 | 仅紧急单 / 被授权 | 该服务单的 | 被派单的那条 | 全部 |
| 回执 | ✗ | ✓ | ✓ | ✓ | ✓ |
| 接服务单 | ✗ | ✗ | ✓ | ✓ | ✗ |
| 接核验单 | ✗ | ✗ | ✗ | ✓ | ✓（仅补录） |
| 发起核验单 | 紧急键 | ✗ | ✗ | 手动补建 | 手动补建 |
| 关闭核验单 | ✗ | ✗ | ✗ | ✓（必须填结论） | ✓（仅补录） |
| 修改关系链 | ✗ | ✗ | ✗ | ✗ | ✓ |
| 修改阈值 / 等待时限 | ✗ | ✗ | ✗ | ✗ | ✓ |
| 导出数据 | ✗ | ✗ | ✗ | ✗ | ✓ |

### 1.5 一条必须守住的边界

**关系人（含家属）不能关单，只能回执。** 家属回一句"没事"只是证据，判定权在承办人手上——对应报告"异常判定权必须保留在人手中"。

## 三、处置端（社区工作者 / 承办人）

### 3.1 形态：**不做后台，做"点开就能办"的单页**

一线人员不会为了填工单去登录一个后台。真实行为是：收到提醒 → 点开看一眼 → 打电话 → 回一句"没事"。
如果要求"登录系统 → 找到工单 → 打开表单 → 填 8 个字段 → 提交"，第 3 周就没人用了，指标全部失真。

**形态已定**：一张卡片 + 一个单页，不做带导航的后台。

**但 v1 不实现通知通道。** 8 周实验目前以口头描述为准，落地时要重排；通知通道（微信服务通知需资质、企业微信需组织开通）不该卡住系统开发。

| 阶段 | 做什么 |
|---|---|
| **v1（现在）** | 响应式 Web 单页（手机浏览器可用），打开就是"我名下"列表；提醒靠系统内红点 + 管理员催办 |
| **v1.5** | 接企业微信 / 公众号模板消息，卡片点开直达单据 |
| **二期** | 微信服务通知（需资质）、短信、外呼 |

所以"15 秒办完"仍是设计目标，但 v1 的验收标准是：**手机浏览器打开 → 3 次点击内填完结论**。

### 3.2 首页三块

| 区块 | 内容 | 排序逻辑 |
|---|---|---|
| **我名下**（待承办核验单） | 卡片列表 | 按 SLA 剩余时间升序，超时标红 |
| **待接**（服务单） | 只显示"已派给关系人、15 分钟未接"才落池的 | 按距离升序 |
| **我负责的老人** | 该承办人负责范围内**已建档**的老人（按监测等级筛选） | 按"最近无信号天数"降序 |

> **建档范围不设人群门槛。** 只要老人本人接受，就建档——独居、空巢、与配偶同住、与子女同住都收，账号可停用、可删除。不按"独居/空巢"筛选。
>
> 但有一个副作用必须处理：建档放开后，会有相当一部分老人**只建了档、没有可用信号**（不用小程序、不打卡）。这类老人不能算 D/Q，否则看板全是"信息不足"。所以档案里必须有**监测等级**（见 5.1）。

### 3.3 核验单卡片（字段是硬要求）

```
┌──────────────────────────────────────────────┐
│ 张桂芳 · 78 岁 · 3 栋 201          ⏱ 剩 12 分 │
│ ──────────────────────────────────────────── │
│ 触发：连续 2 天未确认日历                       │
│ 偏离度 D 0.72 ／ 置信度 Q 0.61  → 强证据偏离    │
│                                              │
│ 依据信号（可展开）                              │
│  · 10-17 未撕日历       ← 强确认信号缺失        │
│  · 10-17 全天未打开      ← 弱活动证据           │
│  · 10-15 志愿者上门      ← 最近一次人类接触      │
│                                              │
│ 已通知：女儿 李敏 14:02（主责·未读）             │
│        志愿者 王姨 14:02（知会·已读未回）        │
│                                              │
│ 近况：近 7 天打卡 5/7，10-16 起中断              │
│                                              │
│ [ 打电话 ]  [ 去家里 ]  [ 转社区 ]              │
└──────────────────────────────────────────────┘
```

**四条不可省：**
1. **每条预警必须能看到"因为什么"**——信号逐条列出，可点开看原始记录。这是"可溯源"要求的落地，也是核验单的核心信息。
2. **D 和 Q 分开显示**，不能合成一个"风险分"。合成一个数就回到了"是否异常"的二元判断，L3 的设计就没了。
3. **关系链通知记录要显示在卡片上**（谁、几点、读没读）。这是"为什么轮到我"的解释，也是家属确认率指标的数据源。
4. **SLA 倒计时**。没有倒计时，升级机制就是纸面的。

### 3.4 处置结论：**4 个按钮，15 秒填完**

| 按钮 | 落库 | 计入指标 |
|---|---|---|
| **没事** | result=normal | 无效核查 +1 |
| **有事，已处理** | result=abnormal_handled | 真异常 +1 |
| **联系不上，转社区** | result=unreachable_escalated | 升级 +1（不计无效） |
| **老人说不用管** | result=declined | 无效核查 +1（单列原因） |

**必填只有两项**：方式（电话/上门，点上面动作时自动带）、备注（≤50 字，可空）。
**耗时自动算**（点"打电话"到点结论的时间戳差）。

> 如果一次处置要填 2 分钟，承办人就会瞎填，指标就废了。**表单长度直接决定数据质量。**

**"没事"和"老人说不用管"必须分开**。前者是系统判断对了但没必要上门（真·无效核查），后者是老人主动拒绝（不能算机制的问题）。混在一起，指标会被质疑。

> **紧急单的按钮标签不一样**：第一个写作「**已上门确认，没事**」；另加一个「**电话确认，未上门**」——选它会自动补一张"当日上门"待办，当天不闭环就继续升级。理由见 6.4。

### 3.5 服务单：**先派关系人，再进池**

v0.1 写"抢单制、距离扩圈"，与老人端 6.2 的"30 分钟内有人联系您"对不上——纯抢单池 3 km、30 分钟才扩圈，承诺兑现不了。

修正为三段：

| 段 | 动作 | 时限 | 累计 |
|---|---|---|---|
| 1 | 派给该老人的**服务承接人**（责任组优先，其次结对志愿者） | 15 分钟 | 15 |
| 2 | 无人接 → 进公共池，按距离扩圈（3 → 5 → 10 km） | 10 分钟 | 25 |
| 3 | 仍无人 → 转管理员，管理员指派或联系签约服务商 | 当日 | — |

> 段 1 + 段 2 = 25 分钟，留 5 分钟给承接人打电话——这样才凑得上老人端"30 分钟内有人联系您"。**池子时限不能设 30 分钟，否则一进池就超承诺。**

**接单资质：**

| 单型 | 谁能接 | 说明 |
|---|---|---|
| 代购、维修联系、上门看一眼 | 任何服务承接人（**含家属**） | 无资质要求 |
| 陪同就医 / 陪同取药 | 家属、志愿者、签约服务商 | 需成年、能离场 |
| **代取处方药** | **任何人不得单独完成** | 处方药须本人或直系家属；志愿者只能陪同 |

> "看病取药"这个键名可以留，但系统里的服务单要拆成"**陪同就医**"和"**陪同取药**"两张子单——**不能派给志愿者一张"代取药"单**。这是合规问题。

**指标归属**：服务单不计入无效核查（报告口径），单独计"服务时长"，可对接时间银行。

> 服务单是"事办没办完"，核验单是"人有没有事"。**两种单绝不能混在一个列表里**，结论字段也完全不同。

### 3.5b 账单与余额（服务单的钱）

服务单一旦涉及代购、维修，就要有人先垫钱。规则：

```
服务完成 → 承接人填金额 → 生成账单 → 推给家属
家属端：余额 200 元 ｜ 本单 38 元 ｜ [确认支付]
余额不足 → [去充值]
```

| 项 | 规则 |
|---|---|
| 谁付 | 家属（主责优先）。家属可提前预存余额 |
| 账单状态 | 待确认 → 已支付 / 已免单（家属自担时直接免单） |
| 金额上限 | 单笔 500 元，超出需管理员确认（防代购单被滥用） |
| **支付通道** | **v1 不接真实支付**，只做记账。微信支付要商户号与企业主体，学生项目办不下来 |

> 边界：**支付通道预留，当前为记账模式。** v1 不接真实支付——微信支付需要商户号与企业主体。余额是系统内的记账数字，「支付」即确认扣减。

### 3.5c 一位家属对应多位老人：通知合并

一个女儿同时是爸妈两位老人的主责人，如果一次触发收两条通知，她会烦，然后关通知。

规则：

- 同一人 30 分钟内收到的多条通知 → **合并成一条**
- 卡片标题写"2 位老人今天还没消息"，点进去逐个处理
- 回执仍是**逐人**的，不提供"一起确认"（一人的状态不能替代另一人）

### 3.6 拒单 / 转单

**必须存在"拒单"，且必须填原因**（不在辖区 / 正在处理紧急 / 不熟悉该老人）。
没有拒单出口，承办人会用"已完成"来逃避，数据立刻污染。

## 四、关系人端（家属 / 结对志愿者）

### 4.1 通知通道：v1 只做系统内，通道后接

31.8% 的家属担心"我可能没法及时看到通知"（报告四（三））。所以通知不能只发一次——但 v1 先把"发得出去"做对，再谈"发得够狠"。

| 阶段 | 通道 | 说明 |
|---|---|---|
| **v1** | **系统内通知**（打开小程序/Web 可见）+ 管理员"未读超时"清单 | 不依赖任何外部资质，今天就能做 |
| v1.5 | 企业微信 / 公众号模板消息 | 需组织开通 |
| 二期 | 短信、电话外呼 | 要钱、要通道，且需已读回传 |

**v1 的诚实兜底：家属不看，就没有人知道。**

所以 v1 必须配一个"**超时未读清单**"——管理员每天看一次，谁没读、哪张单卡住了，由管理员打电话。这不优雅，但它是 v1 唯一能兑现"30 分钟"的办法。

> **v1 的可靠性来自人（管理员催办），不来自通道。** 通道是 v1.5 的事。

### 4.2 回执：三个按钮

```
妈今天还好吗？

[ 我去看过了，没事 ]
[ 打过电话，没事   ]
[ 联系不上，请社区去看看 ]
```

- 回执**不等于关单**，只是证据；承办人仍需确认
- 回执即停止升级计时
- 第三个按钮 → 立即升级，不等超时
- **只有主责的回执能停计时**；知会点了只记录，不改变路由

### 4.2b 同一张卡片上的第二类事：服务单

老人按了"买东西""东西坏了"，如果这位家属持**服务承接人**身份，他会同时收到一张服务单卡片：

```
妈想买：米、降压药（她说的）
[ 我去办 ]  [ 我不方便，转给别人 ]
```

- 家属接单，走的仍是 3.5 的同一套单，只是派单起点就是他自己
- 不接就落池，不影响关系链
- **家属接单不计入任何考核**，只记服务时长

### 4.3 近况简报

最近 7 天：打卡 N/7、最近一次服务、最近一次家属确认、有没有未处理的服务单。
**每条带来源标注**（"来源：打卡日志"），不写"老人状态良好"这种无依据的结论。

### 4.4 文案边界

家属端**不出现"预警""异常""风险"**，用"今天还没消息"。
老人会看到家属的手机。一句"异常预警"能让老人第二天就把手机收起来——这是产品问题，也是伦理问题。

### 4.5 代管模式

失智或不会用手机的老人（报告局限 4 明确排除常规交互），走**家属代管**：家属在自己端代打卡、代发起。系统里 `elder.mode = proxy`，老人端不激活。

## 五、管理端（社区管理员）

### 5.1 建档：建的是什么档、谁建、多久

**建档 = 给一位老人建一条系统档案。** 字段只有这些，不收集病史、收入、身份证号（对应报告三（四）最小化收集）：

| 字段 | 必填 | 说明 |
|---|---|---|
| 姓名 / 出生年 / 住址 | ✓ | 出生年只到年，不到日 |
| 关系链（责任组） | ✓ | 有序列表，见 5.2 |
| 监测等级 | ✓ | A/B/C/D，见下表 |
| 慢病标签 | ✗ | 仅用于日历内容个性化，**不参与风险计算** |
| 代管模式 | ✗ | proxy / self |

**监测等级**（建档时按信号可用性自动判，管理员可改）：

| 等级 | 条件 | 系统做什么 |
|---|---|---|
| **A 全量** | 会用小程序，有打卡 / 打开信号 | 跑 L1–L3，参与预警与看板 |
| **B 事件型** | 有账号但不常用 | **不算 D/Q**，只接四键与紧急键 |
| **C 代管** | 家属代管 | 家属代打卡，信号来源记为家属 |
| **D 仅建档** | 只登记、未开通 | 不产生任何信号，不进看板分母 |

> **这一层是必须的。** 建档放开之后，如果所有人都算 D/Q，一个社区 200 位老人里可能有 120 位永远"信息不足"，看板会像坏了。分等级之后，看板只统计 A 级，B/C/D 单独计数。

**谁建、怎么建、多久：**

| 项 | 说明 |
|---|---|
| **谁建** | 家属注册后填老人基本信息，系统生成 6 位邀请码（7 天有效），**老人端输入邀请码即完成绑定**。管理员只做审核与批量维护 |
| **怎么建** | 单人表单 + Excel 批量导入（批量导入标「暂缓」，见 0.1 节） |
| **多久** | 首批 30–50 人：导入 + 核对关系链，**约 2 小时**；之后随推广增量补 |
| **谁能被建** | **只要老人本人接受就建**，不按独居/空巢筛选；与配偶同住、与子女同住都收 |
| **能不能删** | 能。停用（保留历史数据）或删除（仅限从未产生工单的档案） |

> 建档不是一次性动作。社区推一户建一户，**规模由推广速度决定，不由系统设定上限**。

### 5.2 关系链配置：**这是报告的创新点二，必须做成可视化的**

```
第 1 层  【责任组】李敏（主责）· 李强 · 李娟   ┐ 同步通知
         王姨（结对志愿者·知会）               ┘ 等 15 分钟
第 2 层  陈师傅（承办人·主责）                  等 2 小时
第 3 层  社区值班 / 转介
```

可配项：
- 层数（1–4 层，农村社区可能只有 2 层）
- **第 1 层形态：责任组 / 单点 / 结对志愿者**（默认责任组，**不是必选**）
- 每层 1 主责 + N 知会
- 每层等待时长（默认 15 分钟 / 2 小时）
- 连续 N 次无人响应自动升级（默认 2 次）
- **每个社区独立配置**——换社区只改配置，不改代码

> 实现上就是一个数组 + 几个数字。但**界面上必须是链条的样子**——让人一眼看出「核验顺序是可配置的规则，不是临场判断」。

### 5.3 规则配置（含实验开关）

| 参数 | 默认 | 是否实验变量 |
|---|---|---|
| **路由模式** | 关系优先 | **是**（可切"距离派单"做对照） |
| 第 1 层等待 | **15 min** | 是（v0.1 原为 30，与老人端承诺冲突，已改） |
| 第 2 层等待 | 2 h | 是 |
| 同层同步 / 串行 | 同步 | 否 |
| 基线窗口 | 14 天 | 否 |
| 打卡判定 | 打开=弱信号，点确认=强信号 | 否 |
| 同类型单合并窗口 | 30 s | 否 |
| 切日时刻 | 04:00 | 否 |

> **"距离派单"必须真的能切**。研究设计要与「按距离派单」对照，系统必须真的能切这个模式，否则对照不成立。

> **单社区部署。** 本项目以 1 个社区为对象，不做多租户。但"社区配置"是一等公民——角色显示名、关系链层数与形态、各级时限、功能开关全部可配。换一个社区只改配置、不改代码；各社区按自身需求调整，**总体功能不变**。

### 5.4 工单与台账

- 全量工单列表（筛选：类型 / 状态 / 承办人 / 时间）
- **补录入口**（线下处理过的单，事后补登）——没有补录，台账一定不全
- 一键导出 CSV（字段与报告六（二）口径一致）

### 5.5 指标看板

见第九节。**每个数字旁边必须有口径标注**，否则会被问死（详见 9.2）。

### 5.6 审计

操作日志（谁在什么时候改了谁的档案/参数/结论）、录音留存状态、数据导出记录。
报告三（四）承诺了"数据存于街道指定环境、团队不持有原始数据"——**导出行为必须有记录**，这是承诺的凭证。

## 六、服务端引擎

### 6.1 L1 信号采集

| 信号 | 来源 | 强度 | v1 是否做 |
|---|---|---|---|
| 日历确认 | 老人端点"撕下这一页" | **强确认** | ✓ |
| 应用打开 | 老人端 | 弱活动 | ✓ |
| 四键求助 | 老人端 | 事件型 | ✓ |
| 录音时长 / 是否有录音 | 老人端 | 弱 | ✓ |
| 语音情绪（笑声/哭声/咳嗽） | SenseVoice 音频事件 | 弱 | 二期 |
| 社区服务记录 | 处置端服务单 | 强人类证据 | ✓ |
| 家属确认 | 关系人端回执 | 较强人类证据 | ✓ |
| 智能水/电表 | 外部接入 | 可选 | 接口预留，**不作为前提** |
| 微信运动 | 微信 | 实验性 | ✗（只在打开时更新，不是被动信号） |

### 6.2 L2 个体基线

- 冷启动 14 天；未满 14 天输出 **"信息不足"**，不是"正常"
- 可解释基线：中位数 + MAD / EWMA（承办人能看懂，能审查）
- 模型层（自编码器 / Isolation Forest）作为二期，v1 不做——**先让规则跑通，再谈模型**

### 6.3 L3 分层输出

只输出四格之一，**不输出"是否异常"**：

| | Q 高 | Q 低 |
|---|---|---|
| **D 高** | 强证据偏离 → 派单 | 证据不足 → **补证据**（提示家属确认），不派单 |
| **D 低** | 基线内波动 → 不干预 | 信号缺失 → 不惩罚，等下一轮 |

> "证据不足"这一格是**主动动作**：系统给家属发一条"今天还没联系上，您方便看一眼吗"。它不是"什么都不做"，但也不消耗承办人。

### 6.4 L4 路由状态机

```
预警产生
  ↓
第 1 层：同层全员同步通知（责任组 / 单点 / 结对志愿者）
  ├ 任一人回执"没事" ──→ 待承办人确认 ──→ 关单
  ├ 任一人回执"联系不上" ──→ 立即升级
  └ 15 min 主责未回执 ──→ 第 2 层
第 2 层：承办人（SLA 2 h）
  ├ 处置结论 ──→ 关单
  └ 2 h 未响应 ──→ 第 3 层
第 3 层：社区值班 / 转介
  └ 仍无人响应 ──→ 生成管理员待办 + 标红
```

**兜底规则**：某层无人可用（无家属、志愿者未结对）→ **跳过该层**，不等待。
**"没有人可找"不等于"没人管"**——最终一定落到管理员待办上。

**紧急单是唯一例外：不走逐级。**

老人端 6.2 对紧急承诺"马上有人来，您别动"。按 15 分钟→2 小时的逐级升级，这句话也兑现不了。

```
长按 3 秒（T+0，同一分钟）
  ├→ 全部关系人（主责 + 知会）
  ├→ 承办人（不等第 1 层超时）
  └→ 管理员
       ↓
承办人收到的是两条并行指令：
  ① 立刻拨老人电话
  ② 同时出发 —— 不是"打完再走"
       ↓
电话通了、老人明确说没事 → 降级为普通核验单，当日仍需上门确认
电话不通 / 无人接 / 说不清 → 直接上门，不再等
```

**关键：电话是并行动作，不是前置条件。** 打不通不能成为不去的理由——紧急场景里电话打不通本身就是坏信号。

**紧急单不能靠电话关单。** 老人可能怕麻烦说"没事"，也可能接完电话就晕过去。所以结论里"没事"按钮的标签是「**已上门确认，没事**」；只打了电话的，只能选「**电话确认，未上门**」，系统自动补一张"当日上门"待办，当天不闭环就继续升级。

紧急单**同时跳过 L3 分层与 L4 逐级**，直接全链广播。这是"建单优先于描述"在路由侧的对应动作。

### 6.5 可溯源

每条预警落库时存 `signal_snapshot`（当时用了哪些信号、各自的值、权重、新鲜度）。
没有这个，卡片上的"依据信号"就是编的，指标也无法复核。

### 6.6 幂等与去重

- `client_request_id` 唯一键（老人端生成 UUID v4）
- 同一老人 30 秒内同类型单合并
- 紧急单**不合并**（宁可重复，不可漏）

## 七、工单状态机

**核验单：**

```
待派 → 已通知(第1层) → 待承办 → 已办结 → 已关闭
         │                │
         ├→ 升级(第2层) ──┘
         └→ 取消（老人端撤回 / 管理员撤销）
```

**服务单：**

```
待接单 → 已接单 → 进行中 → 已完成 → 已关闭
           │         │
           └→ 释放 ←─┘（15 分钟未出发）
```

两条链**不共用状态枚举**。硬凑成一套状态机，后面每加一个功能都要打补丁。

## 九、指标怎么从系统里长出来

### 9.1 映射表

| 指标 | 数据来源 | 计算 | 谁产生数据 |
|---|---|---|---|
| **无效核查次数** | `disposition.is_invalid_check` | 按周计数 | 承办人点"没事/不用管" |
| 承办人介入率（报告称"网格员介入率"） | `order.assignee_id` | 承办人处置单 / 全部预警单 | 系统自动 |
| 家属确认率 | `notification.ack_result` | 家属回执单 / 通知单 | 关系人点回执 |
| 首次响应时长 | `order_event` | 触发 → 首次人工动作 | 系统自动 |
| 升级率 | `order_event(action=escalate)` | 升级次数 / 预警单 | 系统自动 |
| **异常识别召回率** | `true_event` 表 | 机制预警真异常 / 全部真异常 | **v1 只建表，不做页面** |
| 结对岗位接续率 | `relation` | 交接成功 / 交接事件 | 管理员登记 |

### 9.2 两个必须写死的口径说明

**① 召回率系统算不出来。** 分母是"试点期间实际发生的全部真异常"，这些事件往往是事后由家属/邻居/社区发现的。**v1 只把 `true_event` 表建好、不做录入页**；等要出这个数时再补一个回溯录入界面，由社区与研究者共同登记。看板上这个数字必须标"人工回溯，下限估计"。

**② 台账口径 ≠ 问卷口径。** 报告六（二）明确说：问卷的 8.7 次/周是自报，试点期是台账计数，**两者不可直接比较**。所以看板上：
- 不许把"问卷基线 8.7"和"试点期 3.2"画在同一根柱子上
- 必须显示"本页数据为台账口径，与问卷自报值不可比"
- 试点前先用台账回溯前 4 周，形成"台账基线"，比较只在台账内做

> 这两条如果不在系统里做，机制的可验证性就是空的。**一个数字配一句口径说明，比十个漂亮的图表有用。**

## 十、功能范围：本期 / 暂缓 / 不做

### 10.1 本期必做（不做机制就不成立）

| 功能 | 理由 |
|---|---|
| 双轨派单（核验指派 / 服务先派关系人再落池） | 两种单结论不同，混了就测不准 |
| 核验单卡片显示信号来源 | 可溯源，核验单核心信息 |
| D / Q 分开显示 | 合成一个分就退回二元判断 |
| 4 键处置结论 + 自动计时 | 台账数据源，表单长度决定数据质量 |
| 关系链可视化配置 | 创新点二 |
| 距离派单可切换 | 报告的对照设计 |
| 通知 + 超时未读清单 + 升级 | 31.8% 家属看不到通知；v1 靠管理员催办兜底 |
| 拒单 + 转单 | 没有出口就会造假数据 |
| 台账 CSV 导出 | 报告承诺的验证数据 |
| 审计日志 | 数据合规承诺的凭证 |

### 10.2 二期增强（有余力再做）

| 功能 | 判断 |
|---|---|
| AI 近况简报 | 有价值，但必须模板化 + 带来源标注；**不能是 v1 阻塞项** |
| 语音情绪信号 | 加分项，二期 |
| 时间银行积分 | 报告已论证积分是兜底（仅 10.5% 列为动力），别投入 |
| 大屏可视化 | 暂缓，v1 不做 |
| 模型层异常检测 | 规则跑通再上，v1 不做 |

### 10.3 本期不做（做了会干扰机制验证）

| 功能 | 为什么不做 |
|---|---|
| **给承办人看"我的无效核查率"** | 一旦变成个人考核，他们就会不填或瞎填，指标立刻失效。**只能看社区层面的汇总** |
| 排班 / 考勤 / 绩效 | 同上，会诱导刷数据 |
| 多社区多租户 | v1 单社区。多租户是纯工程负担；换社区靠改配置，不靠改代码 |
| 自建 App / 公众号 | 先系统内通知，后接企业微信/公众号；自建 App 要审核，v1 不碰 |
| 复杂 RBAC 权限 | 5 个职能身份够了；**关系身份是数据不是权限**，别做成角色 |
| 实时 ASR 自动建单 | 报告已定"录音 + 人工回放"路径，别在 v1 赌识别率 |

### 10.4 四处我建议改（与原设想不同）

1. **处置端不要做成后台**，做成"卡片 + 单页"（3.1）。v1 不做通知通道，只做响应式 Web。
2. **管理端 v1 只做三件：建档导入、参数配置、导出**。看板最后做——它不影响机制运行，只影响展示。
3. **家属端不出现"预警/异常"字样**（4.4）。老人会看到家属手机。
4. **建档不设人群门槛**，愿意用的老人都建；用**监测等级**（A/B/C/D）区分"有信号"和"只建档"，而不是靠缩小人群来控制量（5.1）。

### 10.5 两个不做项，解释一下

**复杂 RBAC 权限。**
RBAC = 按角色给权限：管理员能改配置，承办人只能看自己名下的单。**复杂** RBAC 指角色继承、权限细到某个字段、能动态配策略那一套。我们只有 5 个职能身份、十几条固定规则，代码里写 if 就够。上了复杂 RBAC，配置成本比业务代码还高，换社区时还容易配错——把一个"给管理员开开关"的事做成"配一套权限树"，不划算。

**实时 ASR 自动建单。**
老人按住说话 → 语音实时转文字 → 系统自己判断他要干什么 → 自动生成工单，全程不用人听。不做它有三条理由：

1. 老人方言重、气息弱、背景有电视声，真实准确率比 benchmark 低 10–20 个百分点；
2. 报告五（五）已定"原始录音一律留存，识别失败走录音 + 人工回放"——识别不能是单点依赖；
3. **建错单比不建单更麻烦**：一张错单会派给错的人，还要撤、还要解释。

v1 走"录音 + 承办人听 + 四键选类型"，ASR 是二期增强，不是 v1 前提。

## 十一、与老人端的接口契约

| 老人端动作 | 系统端处理 | 注意 |
|---|---|---|
| 撕下日历 | 写 `calendar_confirmed` 强信号 | 点 × 关闭不算确认 |
| 按四键（不录音） | 建服务单 | **按钮本身就是信息**，录音是增强 |
| 按住录音 | 建服务单 + 挂音频 | 音频永久留存，撤回不删 |
| 长按紧急 3 秒 | 建核验单，**跳过 L3 与 L4 逐级**，全链同时通知 | 建单优先于描述 |
| 回执页"30 分钟内有人联系" | **由服务端按当前配置生成话术** | 承诺时限是配置项，不能写死在前端 |
| 10 秒内撤回 | 单据置 cancelled，音频保留 | 已被接单则不可撤 |

> **回执话术必须由后端下发**。前端写死"30 分钟"，管理员把等待时限改成 20 分钟，承诺就假了。报告说"承诺必须兑现"，兑现的前提是话术跟着配置走。

### 11.1 承诺与机制必须对得上

老人端 6.2 的三句承诺，系统端要能逐条兑现。v0.2 核对结果：

| 老人端承诺 | 系统必须做到 | v0.1 能否兑现 |
|---|---|---|
| 紧急「马上有人来，您别动」 | 全链同时通知 + 承办人 5 分钟强制待出发 | ✗ 逐级升级必然超时 → 已改（6.4） |
| 「30 分钟内有人联系您」 | 第 1 层 15 分钟内响应，否则升级，第 2 层再 15 分钟 | ✓ 已改（第 1 层 30 → 15 min） |
| 「今天之内有人联系您」 | 服务单 24 小时内派出并有人接 | ✓ |

**已定：第 1 层等待 15 分钟。** 30 分钟一升级就超时，那句"30 分钟内有人联系您"在升级场景下就是空话。改机制，不改话术。
